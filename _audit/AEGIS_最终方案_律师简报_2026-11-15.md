## 一、委托人的目的与需要的结果（本方案的北极星）

### 1.1 目的（Why）
- 把 AEGIS 从"源码公开但收不到钱"变成"德国 / 欧盟 B2B 愿意签、签了能收钱、收了能续费"的生意。
- 全程不牺牲产品核心卖点：**本地优先、零回拨、气隙可用、数据不出客户环境**。
- 以个人（居住于中国北京）身份起步，但把个人在法律责任、税务、采购准入上的劣势压到可控。

### 1.2 需要的结果（What）
1. 一份德国律师能据此直接出**书面意见**的简报（本文件）。
2. 一套**修完即可合规收费**的 P0 清单——不修就收费 = 许可可能无效 + 个人无限责任。
3. 一套**能守住付费墙**的许可文本与商业模式（尤其闭源模块边界、Change Date 按版本重新计时）。
4. 一条**气隙客户也走得通**的法务 / 数据路径（远程支持不落地个人数据）。
5. 一个明确的判定标准：**现在不能收费 / 修完 P0 才能收费**。

## 四、定稿方案

### 4.1 许可 backbone：BSL 1.1 + 商业许可（双轨，不并列 AGPL）

| 候选 | 结论 |
|---|---|
| MIT（原始） | 允许免费商用 + 去署名，收不到钱——弃用 |
| AGPL | 牙齿只在"对外网络服务 / 分发"，德国内网客户咬不到——弃用，且不得与 BSL 并列 |
| 闭源 | 丢掉 GitHub 信任 / 星标漏斗——弃用 |
| **BSL 1.1 + 商业许可** | **采用**：源码可见获客，但"生产 / 商业使用"本身受限，内网商用也要买 |

**BSL 参数块（定稿，待律师确认）**

```
Business Source License 1.1
Parameters
  Licensor:             Yang Jie (Jerome Young)
  Licensed Work:        AEGIS v1.0.0 — Secure Edge Collaboration Workbench
  Additional Use Grant: Non-production use (evaluation, development, testing,
                        training) is permitted. Production use is permitted for
                        organizations with fewer than ten (10) full-time equivalents
                        AND consolidated annual revenue below EUR 2,000,000 in the
                        most recently closed fiscal year, counting the licensee
                        together with all affiliates it controls or is controlled by.
  Change Date:          2030-11-15
  Change License:       Apache License, Version 2.0   ← 律师书面确认项
Terms / Covenants / Notice：MariaDB 官方逐字，不改
```

- **免费额度写进 AUG**（<10 FTE 且合并营收 <€2M，关联企业合并计算反规避），不另挂 AGPL。
- **AUG 只授权不设限**：删去末尾 "All other production or commercial use requires a commercial license"（那是 BSL 自身效力，重申可能被认定在 AUG 里塞了限制）。
- **SPDX 头用标准标识符 `BUSL-1.1`**（SPDX 官方条目，未弃用）；全文放 `LICENSES/`（REUSE 布局）。
- **Change Date 上限 4 年，按版本重新计时**：2030-11-15 对 v1.0.0 顶格；发 v1.1 时该版本重新起 4 年窗口——版本节奏本身是商业策略。
- **Apache-2.0 作为 Change License**：按 BSL 自带 `compatible` 定义（"can be included in a program with software provided under GPL v2 **or a later version**"）合格；先例指向 Sentry。**列为律师书面确认项，不因此改架构。**

### 4.2 收费结构

- **主：年订阅**——合规价值持续（法规变动、CVE 修补、连接器与模板更新），订阅把"持续交付"与"持续收钱"锁死。
- **辅：永久许可 + 年维保 20–25%**——给德国医院 / 公共部门的 CapEx 口子；断维保只停更，不锁旧版。
- **不做纯一次性买断**——无后续抓手，产品必须长期维护。
- **SLA 写死频率**（季度模板更新 / 安全补丁 7 个工作日内），不写"随时响应"——订阅是负债，一个人干写虚了第一年就被拖死。
- **定价方向**：Starter ≤5 席 €4,900/年；Business ≤50 席 €24,000/年；Enterprise 不限席 €75,000+（含气隙指导、定制模块）。零品牌起步阶段，前 3 家给引入价 €1,900–2,900 换案例 / 推荐语，第 4 家起回牌价并官网公示（有牌价才有锚）。企业功能按包拆卖（SIEM 导出、集中管控等），比整包更容易被采购拆单批准。

### 4.3 付费价值切分（守住付费墙）

企业版功能，天生连客户自己的外部系统，不破坏零触网：RFC3161 TSA 批量时间戳、SIEM 导出、HSM/PKCS#11、多实例集中管控、合规报告生成、审计链司法存证。

**闭源模块边界（P0）**——BSL 写"derivative works 适用本许可"且 Change Date 后整批转 Apache，一旦企业模块被认定为核心衍生品，付费墙会在 2030 年自动消失。可执行判定标准（写进 `docs/LICENSING.md` 并纳入门禁）：

- ❌ 衍生：import 核心源码、共享源码目录、修改核心文件后打包、编译期静态链接核心逻辑
- ✅ 非衍生：独立进程 / 独立服务，仅走 HTTP / WS / CLI 边界；不含核心源码片段；独立仓库或独立目录 + 自己的版权头

### 4.4 激活机制（气隙友好）

**离线 ECDSA 签名 `license.json` 本地导入**：签约绑定客户 ID / 席位 / 到期 / 功能位，客户端用内置公钥本地验签，全程不联网；可选"90 天在线刷新"仅作增值、不在必需路径；复用现有 ECDSA 能力，零新增依赖。
局限：离线许可技术上拦不住席位拷贝 → 靠合同审计条款（`COMMERCIAL-LICENSE.md §5`：24 个月席位记录 + 年度声明 + 抽查权 + 超额补缴 + 虚假陈述终止）与受监管客户自报。

### 4.5 远程支持数据路径（P0，德国客户最先卡这里）

北京 → 德国，只要支持能"看到"客户系统里的个人数据（远程桌面 / 日志 / 截图 / 样本），法律上即：成为 **GDPR Art 28 处理器**（须签 AVV）＋ 数据在中国处理属**第三国传输**（须 Art 46 机制：SCC 2021/914 Module 2 + TIA）＋ 客户追问中国《数据安全法》《个人信息保护法》下的数据调取风险。三条解法，按成本从低到高：

1. **设计上不落地数据**：支持只做屏幕共享 + 口头指导，禁文件传输、禁保存会话日志与截图，写进 SOP 与合同；
2. 支持前签 **AVV + SCC + TIA**（已有 `docs/compliance/DPA.md`、`SCC.md`，需补 TIA 一节）；
3. 大单交**德国本地集成商做一线支持**，你不接触数据（顺带解决主体问题）。

### 4.6 责任、续约与产品边界（条款层）

- **责任上限金额与风险匹配**：医疗脱敏场景下"上限 = 前 12 个月费用（可能仅 €5k）"会被认为与风险显著不成比例。建议上限 = **保险限额**（€1M / €3M，保单作附件）或 **年费 3–5 倍** + 保险。不可限制：故意、重大过失、生命 / 身体 / 健康损害、ProdHaftG、cardinal obligation 的简单过失（只能限到典型可预见损失）。
- **续约与调价（§307 BGB 高风险）**：静默自动续约须给明确机制 + 提前 30–90 天终止权；不得写"可随时调价"，改为续约时按 CPI 或明确公式调整，且客户有终止权。
- **MDR 边界**：`Intended use: administrative de-identification and secure collaboration. Not intended for diagnosis, treatment or clinical decision-making.` 写进 README / EULA，UI 与服务范围不碰临床流程。
- **公共采购现实**：德国公立医院受 VgV/UVgO 约束，个人主体资质 / 财报 / 保险 / 参考项基本零分；先做私立诊所 / 医疗 IT 集成商 / 工业客户，攒 3 个可公开案例再谈公立。
- **为何必须设主体**：CRA 罚则上限 €15M 或全球营业额 2.5%（取高）；PLD 2024/2853 把软件纳入"产品"，2026-12-09 起适用，缺陷软件可追严格责任。P0-2 是责任量级问题，不是体面问题。

### 4.7 销售话术（口径要准）

不说"未授权软件 = 合规事故"（过头，易被客户法务否）。改说两层：
- **采购 / 审计层**：ISO 27001 / TISAX 中"未纳管软件 / shadow IT"是 finding，IT 部门不敢留；
- **责任层**：无厂商合同 = 无保修、无责任上限转移、出事没人背。

## 六、给律师的 10 个问题

1. BSL 逐字文本 + 参数块同页，是否仍构成"修改本许可"？（Covenants 第 4 条）
2. Apache-2.0 作为 Change License，按 BSL 自带 `compatible` 定义是否合规？请书面确认（先例：Sentry）。
3. AUG 的"<10 FTE 且合并营收 <€2M + 关联企业合并"是否满足"不施加额外限制"，反规避是否足够？
4. 企业闭源模块的"独立进程 + API"边界，是否足以避开 derivative works？
5. 个人 vs 有限责任主体签约，BGB §305 ff. 下责任上限的有效性；上限按"保险限额"还是"年费倍数"更稳？
6. 远程支持触发的 Art 28 / Art 46（SCC + TIA）/ Art 27 代表，边界怎么划？
7. 订阅合同的续约与调价条款，怎么写才不被 §307 打掉？
8. CRA：是否构成 manufacturer；自我评估能否覆盖 CE 路径；支持期"相称"如何举证？
9. 中德税收协定下服务型 PE 阈值；反向征收发票必备要素；B2B-only 条款是否足够排除消费者法适用？
10. 含 AES-GCM / ECDSA 的软件出口分类（中国侧为主）与 EU 5D002/5D992 适用；是否需要年度通报？
